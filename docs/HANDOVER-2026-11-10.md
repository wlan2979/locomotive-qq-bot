## 二、这次任务犯的错

按严重程度排，每条都写清「现象 → 原因 → 影响 → 是否已修」。

### 错误 1：CI 红了还发版（最严重）

**现象**：v4.2.0（`feed936`）和 v4.2.1（`10196ef`）两次提交的 CI 都是 `failure`，Release 照发。提交信息里写「33 项单元测试通过」「34 项单元测试通过」，Release 正文也照抄。

**原因**：本地跑完测试就打包发布，CI 在后台异步跑，**从没等过它**。v4.2.1 的发布时刻 18:23:46，CI 18:24:36 才跑完判失败 —— 发布根本没等 CI。

**影响**：对外宣称的验证状态不成立。用户拿到的包对应的代码，CI 是红的。

**已修**：CONTRIBUTING 增加硬约束「CI 未绿不打 tag、不发 Release」。v4.2.2 是第一次严格按这个流程走的（`dd510d0` → CI 绿 → 改版本号 → CI 绿 → 打包 → 发 tag）。

---

### 错误 2：同一 tag 的资产被替换 5 次

**现象**：v4.0.0 发布后 40 分钟内，`Locomotive-v4.0.0-Windows-x64.zip` 换了 5 份，`VERSION` 一次没动。

| 时间 | 字节数 | SHA-256 前 8 位 |
|---|---|---|
| 16:43 | 22,612,045 | 92e2da47 |
| 16:57 | 22,434,663 | ca25e84a |
| 17:09 | 22,434,176 | 6651b9d3 |
| 17:2x | 22,612,048 | 0668d125 |
| 17:3x | 22,434,401 | f568fa5e |

**原因**：每修一个小问题就重新打包覆盖同一个 Release 资产，图省事没发新版本。

**影响**：README 里的 SHA-256 随之改写，**哈希彻底失去校验意义** —— 16:57 下载的人无法用当前哈希自证。issue 也无法定位到具体代码。

**已修**：v4.1.0 起每个版本独立 tag、独立资产；CONTRIBUTING 写明「同一 tag 资产只上传一次」。

---

### 错误 3：tag 与 asset 脱节

**现象**：v4.0.0 的 tag 指向 `f20582c`（协议解耦那次提交），但 Release 里的二进制是最新构建 —— 两者内容不一致。

**原因**：tag 是创建 Release 时自动打的，之后代码一直在变，tag 没动。

**影响**：想用 tag 复现构建的人，拿到的源码和下载的 EXE 不是一回事。

**已修**：v4.1.0 起流程固定为「改版本号 → 提交 → 等 CI → 打 tag → 发 Release」，tag 必须指向版本号所在的那个提交。

---

### 错误 4：CHANGELOG 回溯改写，同一版本条目自相矛盾

**现象**：
- 4.0.0 条目的「变更」里写「移除历史遗留模块，`bot/` 从 24 降到 16」，但同一版本「已知限制」里又写「含历史遗留模块，暂未裁剪」—— 同一版本自相矛盾。实际这次变更发生在 **4.1.0**。
- 4.1.1 条目写「旧 id 会自动迁移到 `default`」，但那个提交的 message 明说「旧数据不迁移」—— 真正的迁移在 **4.2.0**。
- 4.0.0 底部的链接指向已被删除的 tag，是死链。

**原因**：每次发新版时顺手往旧条目里补内容，没有「历史条目只记录当时事实」的纪律。

**影响**：CHANGELOG 从「可信的变更记录」退化成「一份随时会被改写的说明」。

**已修**：4.2.2 清理（删掉误归的条目、修正迁移表述、处理死链）。**但纪律需要后续遵守**。

---

### 错误 5：文档声称改了，实际没改

**现象**：v4.1.1 那轮的 CHANGELOG 写「README 路线图勾选『确定对外许可』」，但 README 里那条一直是 `- [ ] 补作者声明，确定正式开源许可证`，既没勾、措辞也没改。

**原因**：改文档用的是脚本替换，脚本打印了 `OK` 就当成了 —— **没有回头 grep 验证目标字符串是否真的变了**。

**影响**：用户看到的是「文档说改了」和「文档实际没改」并存，比不写更糟。

**已修**：4.2.2 修正并 grep 复核。**改文档后必须 grep 目标字符串**，不能只信脚本输出。

---

### 错误 6：`.gitignore` 把构建必需文件排除

**现象**：v4.0.0 重置仓库时，`src/Locomotive.spec` 根本没进仓库，但 README 写着「spec 已改为全相对路径」。

**原因**：`.gitignore` 用了 PyInstaller 官方模板，里面有一行 `*.spec` —— 把项目自己的打包配置也忽略了。`git add -A` 不会报错，只会静默跳过。

**影响**：别人 clone 下来没法打包；README 的描述是假的。

**已修**：加 `!src/Locomotive.spec` 例外。**重置仓库后应该核对「README 提到的文件是否真的都在」。**

---

### 错误 7：误提交测试产物

**现象**：`frozen-engine-test/` 目录（含 `engine-ready.json`、`result.json`）进了仓库。

**原因**：删本地文件时路径写错（删了 `src/frozen-engine-test`，实际在仓库根）。

**影响**：仓库里多出 4 个无意义文件；虽然不含密钥，但不干净。

**已修**：`git rm --cached` + 加 `.gitignore`。

---

### 错误 8：宣称了但没接上的功能（引擎锁）

**现象**：README 和 `docs/ACCEPTANCE.md` 都写「不同 `--data-dir` 可以并行多开」，实际第二个实例点连接必然失败。

**原因**：`_acquire_single_instance(lock_dir)` 收了 `lock_dir` 参数，**函数体里一次都没用**，锁仍是模块级常量端口 `47201`。窗口层按目录放开了，引擎层没放开。

**影响**：多开只成功了一半，而且是用户点了才会发现的那种失败。

**已修**：v4.2.1 改为命名互斥量 `Local\Locomotive.Engine.<路径哈希>`，并补测试（不同目录各自持锁、同目录互斥）。

**教训**：**写「支持 X」之前，实际跑一遍 X**。参数收了不用，是最难发现的那类 bug。

---

### 错误 9：失败时日志是空的

**现象**：引擎锁冲突 → `return 3` → 界面提示「请查看日志」→ 打开 `bot-process.log` 是空文件。

**原因**：日志用 `"w"` 截断模式打开，`return 3` 之前一个字都没写。

**影响**：诊断链断在最关键的一环 —— 用户按提示去看，什么都看不到。

**已修**：v4.2.1 补 `print` 再 `return 3`；日志改追加 + 5 MB 轮转（截断模式还和 `--supervise` 互相抵消，看门狗越勤快越看不到崩溃现场）。

---

### 错误 10：数据迁移不是原子操作

**现象**：`default_data_dir()` 用 `shutil.copytree` 直接复制到目标目录，中途失败（磁盘满/权限/进程被杀）会留下**半套数据**的目录。

**影响**：下次启动 `current.exists()` 为真，跳过复制，用户看到「记忆没了」「机器人配置空了」，而旧目录还好端端在那儿。

**已修**：v4.2.1 改为 staging（`<目录>.migrating`）+ rename。

---

### 错误 11：中文 print 在 cp1252 下崩溃（CI 失败根因）

**现象**：v4.2.0 / v4.2.1 的 CI 都挂在 `test_supervise_*`。

**原因**：`supervise` 里直接 `print` 中文，GitHub runner 的 stdout 是 **cp1252**，抛 `UnicodeEncodeError`。本机是 GBK，所以本地跑一百遍都不会暴露。

**影响**：两个版本带着红的 CI 发出去了。

**已修**：v4.2.2 改为写 UTF-8 日志文件，stdout 仅在编码支持时输出。

**教训**：**本机环境 ≠ CI 环境**。已知差异至少两类：stdout 编码（cp1252 vs GBK）、临时目录短名（`RUNNER~1` 的 8.3 格式）。

## 三、需要改进的地方

### 流程

1. **CI 未绿不发 tag**（已写进 CONTRIBUTING，关键是执行）
2. **发布前对照 `docs/ACCEPTANCE.md` 走一遍**，至少跑第 1、3、4 条（WebView2 提示、单实例、多开）
3. **一天发 9 个版本不是好节奏**。版本号涨得比可信度快 —— 用户看到 v4.2.2 会觉得「在迭代」，实际是在补前一个版本的漏洞
4. **发布说明里别写「N 项测试通过」除非 CI 也绿**

### 文档

1. **CHANGELOG 只追加，不改历史条目**。发现旧条目写错了，用新条目写「更正：xxx」
2. **改完文档 grep 验证目标字符串**，不要只信脚本的 `OK`
3. **写「支持 X」之前实际跑一遍 X**（引擎锁那条就是没跑）
4. **README 的数字要能自动核对**（文件数、字节数、SHA），或者干脆不写具体数字

### 工程

1. **新增功能要配能覆盖它的测试**。v4.2.0 加了 4 个测试，但没覆盖「引擎锁按目录」——那正是唯一出错的地方
2. **跨平台/跨环境差异要提前想**：stdout 编码、路径格式、临时目录
3. **锁、迁移、日志这类基础设施，先写失败路径的测试**，再写成功路径

### 验证

1. **`docs/ACCEPTANCE.md` 写了就要跑**。现在它是「一份没人执行过的验收清单」
2. **真实链路只做了一次冒烟**，多轮上下文、图片消息、@ 判定、断线重连、并发消息全没测
